## Context

The codebase currently has terminology inconsistencies that have evolved over time:

1. **"domain" vs "stack"**: The manifest schema originally used `domain` to group related services, but this has been migrated to `stack`. Currently, code uses fallback patterns like `manifest.get('stack') or manifest.get('domain')` to support both, creating confusion about which is canonical.

2. **"service" vs "resource"**: The architecture has shifted from thinking in terms of "services" (business-oriented) to "resources" (deployment-oriented Tilt resources). Function names like `get_app_resources()` exist alongside variable names like `svc` and `service`, and docstrings refer to "services" while the code handles "resources".

3. **Cache keys**: The discovery cache uses `domain_configs` which doesn't align with the `stack` terminology.

4. **Autogenerated files**: Files like `product_autogenerated_domains_index.star` use old terminology.

These inconsistencies make the codebase harder to understand, especially for new developers. Standardizing on "stack" (for logical grouping) and "resource" (for deployable units) will provide clarity.

## Goals / Non-Goals

**Goals:**
- Replace all `domain` manifest field access with `stack` (remove fallbacks)
- Rename `domain_configs` cache key to `stack_configs`
- Update all docstrings and comments from "service" to "resource"
- Rename variables from `svc`, `service` to `resource`
- Rename functions like `_render_product_domains_index()` to `_render_product_stacks_index()`
- Update autogenerated file naming from `domains` to `stacks`
- Ensure no functional changes - purely terminology refactoring

**Non-Goals:**
- Changing manifest file structure (the JSON schema)
- Changing the actual behavior of any function
- Adding new features or capabilities
- Removing support for legacy manifest formats in the loader/parser
- Renaming the `app_resources` cache key (widely used, high risk)

## Decisions

### Decision 1: Keep `app_resources` Cache Key
**Rationale**: The `app_resources` key is used extensively across the codebase (50+ references). Changing it would touch too many files and create high risk of merge conflicts. The term "app resources" is acceptable since it describes the collection of resources for an app.

**Alternatives considered**:
- Rename to `resources` - Rejected due to high touchpoint count and risk
- Keep as-is - Accepted as "app resources" is descriptive enough

### Decision 2: Remove `domain` Fallback Patterns
**Rationale**: Patterns like `manifest.get('stack') or manifest.get('domain')` exist to support legacy manifests. However, all current manifests should have migrated to `stack`. Removing the fallback simplifies code and establishes `stack` as the canonical field.

**Migration approach**:
```starlark
# Before:
stack = manifest.get('stack') or manifest.get('domain') or extract_stack_from_path(path)

# After:
stack = manifest.get('stack', extract_stack_from_path(path))
```

### Decision 3: Update Variable Names Incrementally
**Rationale**: Variables like `svc`, `service` should become `resource`. However, in loops where context is clear (e.g., `for svc in resources`), shorter names are acceptable. Focus on function parameters and docstrings first.

**Priority order**:
1. Function parameter names
2. Docstrings and comments
3. Variable names in outer scope
4. Loop variables (lower priority)

### Decision 4: File Renaming for Autogenerated Files
**Rationale**: Autogenerated files like `product_autogenerated_domains_index.star` should be renamed to use `stacks`. This requires updating both the file generation code and any `load()` statements that reference these files.

## Risks / Trade-offs

**Risk**: Breaking external code that reads `domain` from manifests
- **Mitigation**: This is a **BREAKING** change as noted. External code must migrate to `stack` field.

**Risk**: Inadvertent functional changes during bulk renaming
- **Mitigation**: Each task will be focused on a specific file or small group. Tests must pass after each batch.

**Risk**: Merge conflicts with ongoing development
- **Mitigation**: Tasks are organized by directory to minimize conflict surface area. Complete quickly.

**Risk**: Missing some instances of old terminology
- **Mitigation**: Final verification task will grep for remaining `domain`, `svc`, `service` patterns.

**Risk**: Variable name collisions after renaming
- **Mitigation**: Use `resource` not `res` (too short). In nested contexts, use descriptive names like `app_resource`.

## Migration Plan

1. **Phase 1: Discovery System** (Tasks 1-40)
   - Update `/discovery/` directory files
   - Rename `domain_configs` to `stack_configs`
   - Update manifest access patterns
   - Update docstrings

2. **Phase 2: Engine Topologies Tilt** (Tasks 41-100)
   - Update deprecated system files
   - Update generator files
   - Update resource orchestration

3. **Phase 3: Engine Topologies Platform** (Tasks 101-130)
   - Update platform-level files
   - Update Docker, networking, compose files

4. **Phase 4: Autogenerated File Naming** (Tasks 131-140)
   - Rename autogenerated file references
   - Update file generation code

5. **Phase 5: Verification** (Tasks 141-150)
   - Run full test suite
   - Grep for remaining `domain` references
   - Grep for remaining `service` vs `resource` inconsistencies
   - Verify no `manifest.get('domain')` patterns remain

## Open Questions

- Should we keep `app_resources` as-is or rename to `resources`? (Decision: keep as-is for now)
- Should we update function names like `get_app_resources()`? (Decision: lower priority, focus on internals first)
- How to handle `svc` in tight loops where context is clear? (Decision: focus on function params and docstrings first)
