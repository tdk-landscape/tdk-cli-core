# Design

## Context

See `proposal.md` (Why) for the motivating case. Relevant current behavior:

- Whether an app resource starts automatically is already a single Tilt-native, landscape-wide switch: `RuntimeFlags.resolve()` (`engine/topologies/tilt/resources/orchestrator/apply_runtime_flags.star`) reads `TILT_AUTO_INIT_APPS` into `runtime_flags['auto_init_apps']`, and `_register_replicas(config, auto_init_apps)` (`engine/topologies/tilt/resources/orchestrator/apply_compose_resource_registration.star:117`) passes it straight through as `dc_resource(..., auto_init=auto_init_apps)`. `auto_init` is Tilt's own parameter: `auto_init=False` means Tilt builds the resource's image and creates its container as part of reconciliation, but does not start it until explicitly triggered (`tilt trigger <resource>`, or the Tilt UI/HTTP API). This is exactly the "built but not started" split the proposal needs — it already exists, just as one global flag instead of a per-resource one.
- Sablier's premium implementation (`tdk-cli-extensions/premium/networking/sablier_container_cycle.star`) already assumes the container exists (Traefik's `traefik.docker.allownonrunning=true` plus `sablier.enable`/`sablier.group` labels) and only handles the docker-level stop/start of an existing container. It has no concept of Tilt's own build/create step, and no way to call back into Tilt.
- `engine/lifecycle/orchestrator.star`'s `STARTUP_PHASES` and `should_wait_for_dependencies` compute Tilt `resource_deps` chains per manifest (database, NATS) already; that same data is what a wake needs to decide which other resources to bring up together.
- Tilt exposes an HTTP API on `localhost:10350` (already referenced as the debug/inspection endpoint in `engine/paths.star:652` and as `tilt trigger <resource>` in `cli/src/utils/doctor-runtime.ts:486`) that includes a trigger endpoint equivalent to the `tilt trigger` CLI command. This design relies on that existing mechanism rather than adding a new one to Tilt.
- Real Sablier (`sablierapp/sablier`, already vendored per `traefik_standalone.star`) already holds an incoming request open and serves a wait/loading response until the container it started passes its healthcheck, or a configured timeout elapses — this is stock Sablier behavior, not something this change adds. What's missing is only: (a) getting the container into a "created, stoppable" state before it's ever run once, and (b) also reaching into Tilt for anything Sablier's plain Docker start doesn't cover.

**Verified against the live `tdk-erp-system` landscape and an isolated probe (2026-09-26), replacing the preflight guesses below:**
- The user's exact URL, reproduced live: `curl http://api.tdk-erp-system.localhost/api/data-governance/health` returns `404 page not found`, and Traefik's own API confirms why — `GET /api/http/routers/data-governance-api-project@docker` returns `{"message": "router not found: data-governance-api-project@docker"}`. The container (`analytics-autogenerated-data-governance-api-1`) does exist, `docker inspect` shows it ran once, went `unhealthy`, and `exited` hours ago — Tilt's own `uiresource` for it shows `runtimeStatus: pending` (queued to rebuild, `order: 50`, behind whatever else is ahead of it). Traefik drops an exited container from routing entirely because its labels have no `traefik.docker.allownonrunning=true` (this project has no `sablier` block on it at all). So the concrete failure mode observed in production is "crashed and queued for rebuild behind everything else," not only "literally never started" — D3's Tilt-trigger call addresses both, since it doesn't care why a resource isn't running, only that it now should be first.
- A throwaway `Tiltfile` + `docker-compose.yml` (two `busybox` services, one `dc_resource(auto_init=True)`, one `dc_resource(auto_init=False)`, run on an isolated port so the live landscape was untouched) showed: the `auto_init=False` resource gets **no container object at all** (`docker ps -a` shows nothing for it; its `uiresource` stays `runtimeStatus: none` / `updateStatus: none`) until triggered. `tilt trigger <name>` then creates *and* starts it from nothing in one call. This overturns D2's "Tilt pre-creates the container" assumption below — it does not. See the corrected D2/D3/D6.

## Goals / Non-Goals

**Goals:**
- Make "start on first request" work for a resource that has never run this session, using the same manifest opt-in, Traefik wiring, and license gate as today's Sablier feature.
- Reuse Tilt's existing `auto_init` mechanism per-resource instead of inventing a parallel scheduler.
- Keep the free-tier stub/premium-override structure (`sablier_container_cycle.star` in both repos) intact - this is an extension of that module's contract, not a replacement.

**Non-Goals:**
- Redesigning Tilt's build/reconciliation loop or its trigger API. See proposal.md Non-goals for the licensing and footprint boundaries.
- Handling a resource whose `sablier` block is added or toggled while `tdk up` is already running (that already requires a Tiltfile re-eval today, same as any other manifest change).

## Decisions

### D1: Deferred start is `auto_init=False` scoped per-resource, driven by the manifest, not the global flag

Add a `deferStart` key to the manifest's existing `sablier` block (`engine/topologies/tilt/manifest/schema.star`'s `sablier` schema, alongside `enable`/`group`/`sessionDuration`), default `false`. `_register_replicas` (and any other call site that currently receives the single `auto_init_apps` flag for app resources) resolves per-resource auto-init as `auto_init_apps and not resource_defers_start(manifest)` instead of using `auto_init_apps` directly. The resource's **config-gen** and **docker_build** resources keep `auto_init=True` unconditionally (or follow `auto_init_config_gen`, already `True` by default) so the image still builds during `tdk up` — only the running container is held back.

*Alternatives considered:*
- A separate global "cold landscape" mode (e.g. `TILT_DEFER_ALL_APPS`): rejected because it can't express "just this one resource," which is the actual request (one API, not the whole landscape).
- Piggybacking on `TILT_TRIGGER_MODE=manual` wholesale: rejected — that already exists and disables `enforce_migrator_deps` and replica counts landscape-wide; overloading it would change unrelated behavior for every resource, not just opted-in ones.

### D2: Two genuinely different wake mechanisms, chosen by whether a container object exists

Confirmed live: `auto_init=False` leaves **no container object** until triggered — there is nothing for Traefik's Docker provider to discover (no container, no labels, no route), which is a different situation from a resource that ran before and is now `exited` (that container and its labels already exist; Traefik would route to it if and only if `traefik.docker.allownonrunning=true` is present). Docker-label auto-discovery — the mechanism the existing premium Sablier module relies on entirely — can only ever cover the second case. The two cases need different plumbing:

- **Previously-ran, now-stopped/exited** (the case actually reproduced live against `data-governance-api`): today's premium `sablier_container_cycle.star` labels already work once a resource opts in — `allownonrunning=true` is the only missing ingredient, and it's already emitted when `sablier.enable` is set. No new mechanism needed here beyond what D1/D4/D5 add.
- **Never created this session** (the state proven by the `auto_init_probe` test): there is no container to attach Docker labels to, so the route has to come from somewhere else. See D6.

*Alternative considered:* add an explicit `docker compose create <service>` step (without starting) right after image build, so every deferred resource always has a discoverable-but-stopped container from the start, keeping Docker-label discovery as the single mechanism for both cases. Rejected as the primary path: it re-adds exactly the container-creation cost (network setup, volume mounts) to `tdk up`'s critical path that deferring was meant to avoid, just shifted from "start" to "create," and it still needs D6's static route anyway for the moment between `tdk up` finishing and that create step actually completing. Recorded as a possible later optimization (pre-create eagerly to shave latency off the very first request) but not required for this change to work.

### D3: Wake calls `tilt trigger` directly; Sablier's Docker-start only applies to the already-created case

Proven live: `tilt trigger <resource>` alone takes a resource from no-container-at-all to created-and-running, is Tilt's own supported CLI surface (unlike its internal HTTP API, which backs the UI but isn't a documented stability contract), and already produces the exact behavior D1-D2 need. So the wake path shells out to `tilt trigger <resource> <dependency-group members>` (per D5) as its primary mechanism for a never-created resource, rather than asking Sablier to start a container that doesn't exist. For a previously-ran-then-stopped resource (D2's other case), Sablier's existing Docker-level start remains the faster path (no Tiltfile reconciliation needed just to restart an existing container) — the wake logic tries the fast Docker-start path first when a container object exists, and calls `tilt trigger` when it doesn't or when the fast path fails.

*Alternative:* always go through Tilt's trigger regardless of container state, and drop Sablier's Docker-level start entirely. Rejected: it makes every wake pay Tilt's reconciliation overhead even for the common case (a resource that only needs restarting), and it removes the one piece of this feature that doesn't depend on Tilt being reachable at all (Sablier + Traefik + Docker socket keep working even if the Tilt daemon itself is down, e.g. mid-`tilt up` restart).

### D4: A never-created resource's route comes from Traefik's static/file provider, not Docker-label discovery

Since a never-created resource has no container and thus no labels, its Traefik router has to be defined statically. The standalone Traefik generator (`traefik_standalone.star`) already reserves the `@file` provider namespace by reference (`maintenance@file` in `traefik.star`) but does not actually enable it — its `command:` list only sets `--providers.docker=true`; there is no `--providers.file=true` and no generated dynamic-config file or mounted directory today. This change adds both: `--providers.file.directory=/etc/traefik/dynamic` (a new generated directory mounted into the `traefik` service), and, for every resource with `sablier.enable` + `deferStart` set, a generated file-provider entry defining that resource's router/service/middleware ahead of time, pointed at a small always-on wake endpoint (the existing `sablier` container, or a thin sidecar next to it) that performs D3's `tilt trigger` call and then proxies through once the resource answers its healthcheck. Once the real container exists and Tilt takes over its lifecycle normally, the static route and the Docker-discovered one both resolve to the same backend; the static entry does not need to be removed (Traefik prefers the more specific/most-recently-registered router in practice, and the static entry's only job is to exist for the window before the container does).

*Alternative:* forward-declare the resource's Docker Compose service with `deploy.replicas: 0` or similar so a static route isn't needed. Rejected — Compose has no "define the service, register it with Traefik, but truly never create a container" mode short of the `auto_init=False` behavior already confirmed to produce zero Traefik-visible state; a static file-provider route is the only mechanism confirmed to give Traefik something to match against before any container exists.

### D5: Wake group defaults to the resource's own `resource_deps`, `group` still wins if set

`sablier_container_cycle.star`'s existing `_sablier_config` resolves `group` from the manifest, falling back to `stack`. This design changes the fallback: if `group` is not set explicitly, the wake group is computed from the resource's own dependency chain (the same data `should_wait_for_dependencies` in `engine/lifecycle/orchestrator.star` already computes: its database and NATS dependencies) rather than from `stack`. Grouping by `stack` bundled unrelated same-stack resources together for sleep/wake; grouping by actual `resource_deps` wakes exactly what a resource needs and nothing more.

*Alternative:* keep `stack` as the implicit default and require every resource to list its wake group explicitly. Rejected — it silently reproduces today's under-specified default and defeats the point of "wake what's actually needed" for resources that never set a `sablier` block on their dependencies.

### D6: `tdk up`/`tdk doctor` read `auto_init` state, not container status, to report "deferred"

A deferred resource looks, from `docker ps`, identical to a resource that failed to start. `tdk up`'s summary and `tdk doctor` need to check the manifest's resolved `deferStart` (D1) directly rather than inferring "deferred" from container state, so a genuinely stuck resource is never miscategorized as intentionally cold.

## Risks / Trade-offs

- [The static file-provider route (D4) and the Docker-discovered route disagree once the container exists, e.g. stale healthcheck path baked into the static entry] → Keep the static entry's routing rule byte-identical to what the generator already emits for the Docker-label version (same source-of-truth function), so the two can never drift; verified by generating both and diffing in task testing.
- [The wake sidecar (D4) needs both Docker-socket access and reachability to Tilt's `localhost:10350` from inside a container] → Confirm the sidecar can reach the host's Tilt port (already true for the existing `sablier`/`traefik` containers, which already mount the Docker socket per `traefik_standalone.star`); if Tilt runs in a context where the container can't reach it (e.g. Tilt itself in a devcontainer), the sidecar's Tilt-trigger call fails loudly rather than hanging — falls back to whatever error Sablier/Traefik already show on a failed wake.
- [Sablier's Traefik plugin has no first-class webhook for "also call this other URL on wake" (D3)] → Preflight-verify against the vendored `sablierapp/sablier` version's actual hook support (tasks.md 1.2); if it has none, the trigger call moves into a tiny sidecar that watches Docker start events for `sablier.enable=true` containers instead of being invoked by Sablier directly — the never-created case (D3/D4) already needs a sidecar-shaped component regardless, so this doesn't add a new moving part, just gives the already-planned sidecar one more responsibility.
- [A resource's dependency-derived wake group (D5) is broader than intended, waking more than the requester expects] → A resource can still set `group` explicitly to opt out of the computed default; document this in the manifest schema description.
- [The held request during wake exceeds Sablier's own timeout on a large dependency group] → `sessionDuration`/timeout stay configurable per resource via the existing manifest field; document that a resource with a large derived wake group may need a longer timeout.
- [Background auto-commit tooling observed in this workspace pushes partial engine edits] → Land each decision's Starlark and CLI edits together with its snapshot tests in one sitting, per the same mitigation already used in `optimize-runtime-docker-layers`.

## Migration Plan

1. Ship the schema (`deferStart`) and engine changes (D1-D6) in a TDK release, gated the same way the rest of `sablier` already is (premium license required for the real module; free-tier stub keeps returning disabled).
2. In each project with an opted-in resource: run `tdk project --yes` to re-vendor, touch the Tiltfile, rebuild affected images.
3. A resource adopts deferred start by adding `deferStart: true` to its existing `sablier` block; removing it (or the whole block) reverts to today's behavior with no other cleanup needed.

**Rollback:** unset `deferStart` (or the whole `sablier` block) and re-run `tdk project --yes`; the resource returns to normal `auto_init` bring-up immediately.

## Open Questions

- Exact Sablier hook mechanism for D3 (native webhook vs. a Docker-event-watching sidecar) depends on the vendored `sablierapp/sablier` version's capabilities - resolved in tasks.md's preflight phase, does not change the specs or the chosen approach either way, since D4 already requires a sidecar-shaped component regardless of the answer.
- Whether Traefik, when both a file-provider router (D4) and a Docker-discovered router (D2) exist for the same resource name, prefers one deterministically or requires a distinct router name per provider - resolved empirically in tasks.md's preflight phase (task 1.4); at most changes a naming detail, not the approach.
