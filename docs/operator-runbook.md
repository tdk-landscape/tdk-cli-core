# Operator runbook

One page for whoever installs, supports, or releases the TDK CLI. Details live in the linked pages.

## Install and support matrix

| Host | `tdk up` | Other commands |
| --- | --- | --- |
| macOS | supported | supported |
| Linux | supported | supported |
| WSL2 Ubuntu | supported (see [wsl2.md](wsl2.md)) | supported |
| Native Windows | not supported; refuses with "Native Windows is inspect-only" | inspect-only |

`tdk up` needs Docker and Tilt on the host. Run `tdk doctor` to check them.

## Versions `tdk doctor` checks

`tdk doctor` enforces minimums, not exact pins:

| Tool | Minimum |
| --- | --- |
| Node.js | 22.12 |
| Docker Engine | 25.0 |
| Docker Compose | 2.20.2 |
| Tilt | 0.25.0 |
| Bun | 1.2.0 |

The source of truth is `cli/src/commands/doctor.ts` (`MIN_*` constants).

## Generated files and drift

For a file-by-file guide to service outputs, see [Generated service files](generated-files.md).

`tdk up` checks generated service files (under `.autogenerated/`) against their snapshot before Tilt starts. Editing `service.json` and running `tdk up` is the normal loop and is not drift: `tdk up` regenerates the outputs.

- If a generated service file was edited by hand, `tdk up` exits 2 and lists it. Restore the saved content or move the intended change into `service.json`; the CLI also suggests `tdk config regenerate`, which rewrites project files rather than the service output itself.
- `tdk config verify` runs a wider check: it compares generated project files, validates discovered service manifests, and checks generated service snapshots. It prints diffs for project files and names service errors.
- `tdk up --dry-run` runs the same check and exits 2 on drift, so you can see it without starting anything.
- `tdk up --ignore-drift` skips the check and always prints a warning, whether or not anything drifted, because the check did not run.
- A missing `.tdk-contract` snapshot is reported by `tdk config verify` as an error, but it does not block `tdk up`: only files that differ from an existing snapshot count as hand edits. A project with no `.tdk/project.json` is not checked.

## Importing an existing repo

TDK CLI core 1.3.104 is the first release with `buildContext` ([tdk-cli-core#525](https://github.com/tdk-landscape/tdk-cli-core/pull/525), [release 1.3.104](https://github.com/tdk-landscape/tdk-cli-releases/releases/tag/v1.3.104)). Use core 1.3.104 or later before starting imported services. The importer does not detect or enforce the installed core version.

Importer **0.1.1** is the published safeguard release containing [tdk-import#9](https://github.com/tdk-landscape/tdk-import/pull/9) and the documentation from [tdk-import#10](https://github.com/tdk-landscape/tdk-import/pull/10). The published npm tarball has been verified for unsupported-only refusal, dry-run without a plan, and partial Procfile imports. Use the pinned version below; 0.1.0 does not include those guarantees.

Preview the services an existing repository describes, then write the generated manifests:

```bash
npx -y @tdk-landscape/tdk-import@0.1.1 <dir> --dry-run
npx -y @tdk-landscape/tdk-import@0.1.1 <dir> --yes
```

If core 1.3.104 or later is not installed, update TDK before running `tdk up`; older releases cannot build imported services that use `buildContext`. Start the imported stack with `tdk up <stack>` only with core 1.3.104 or later installed.

Helm (`Chart.yaml`) and Kustomize (`kustomization.yaml`) files are not imported. The command refuses a directory that contains only those files. Supported Compose, Dockerfile, `package.json` script, and Procfile services are still imported when those files appear alongside Helm or Kustomize files.

For Procfiles, commands beginning with `node`, `npm`, `pnpm`, `yarn`, or `bun` are eligible for Dockerfile scaffolding. Other processes, including Python, Ruby, Gunicorn, and Poetry, are skipped unless a matching Dockerfile or image exists. The importer can write buildable processes from a mixed Procfile and reports each skipped process; add a Dockerfile or image to import it.

## Cutting a release

1. Bump the version in `cli/package.json`.
2. Run `scripts/release-binaries.sh` to build only. It writes `tdk-linux-{amd64,arm64}`, `tdk-darwin-{amd64,arm64}`, `tdk-windows-amd64.exe`, `tdk-cli-engine.tar.gz`, and `checksums.txt` (SHA-256) into `release-dist-<version>/`.
3. Run `scripts/release-binaries.sh --publish` to build and create a draft release in `tdk-landscape/tdk-cli-releases`. The script downloads every asset, compares bytes with the local build, and only then publishes the release as latest. `--publish-only` reuses an existing `release-dist-<version>/`.
4. The installer verifies each binary against `checksums.txt`.

## License key

`TDK_LICENSE_KEY` is optional. `tdk up` still runs the free stack when the key is unset, invalid, or expired. The cases differ in what `tdk up` does:

| Key state | Premium-bundle request | Premium overlay |
| --- | --- | --- |
| Unset | none | none; Verdaccio and Sablier fall back to disabled public stubs and print a message that they need a license |
| Invalid or expired | made, unless a cached result is still fresh | none for a rejected key; an overlay already in `.tdk/.tdk-out/tdk-cli-ext` stays in use |

- Bundle downloads and entitlement checks (grant or denial) are cached per key under `~/.tdk/cache` and reused for up to 12 hours. For that window a key that was just revoked or has just expired can still be treated as entitled, and a key that was denied is not re-checked until the cache expires. Operators will hit this most often.
- `tdk up` does not revalidate the key or re-vendor `.tdk/.tdk-out/tdk-cli-ext`. A premium overlay created while the key was valid can stay in use after the key expires.
- DDD is public code gated separately by `tdk resource --ddd`; it is not a stub.
